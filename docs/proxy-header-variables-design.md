# 反代 Header 变量设计

> 编写时间：2026-11-12T17:39:11+08:00
>
> 状态：已按用户授权完成本地实现；使用说明见 [反代 Header 变量](proxy-header-variables.md)，验证范围见文末。未启动开发服务、生成发布构建或执行提交。

## 1. 目标与现状

允许在反代路由的请求头和响应头值中引用当前请求信息，例如来源 IP、访问域名和请求标识。保存草稿并发布后，对新请求生效。

原有 `requestHeaders` / `responseHeaders` 为字符串映射，控制台通过 JSON 文本框编辑；后端校验 Header 名称、保留字段、CR/LF 和 8192 字节上限。旧模式的请求头在代理 Rewrite 中设置，响应头在执行路由动作前写入，代理后端的同名响应头还可能被追加进来。

首版限定代理动作 `proxy`，覆盖普通 HTTP、SSE 和 WebSocket 握手。变量只用于 Header 值，不用于 Header 名称、后端地址、路由路径、响应正文或跳转地址；升级后的 WebSocket 消息不做替换。

## 2. 配置结构与兼容

保留两个字符串映射，在路由增加可选布尔字段 `headerVariables`，默认 false，省略时不写入 JSON。

| 配置 | 行为 |
| --- | --- |
| 缺失 / false | Header 值按原有固定字符串使用，包括美元符号和看似变量的文本 |
| true | 编译、校验并展开 Header 变量；请求头和响应头共用同一开关 |

采用显式开启，避免已有 Header 中的 `${...}` 被升级后的程序重新解释。已有草稿、已发布配置和历史版本不做自动转换；原始模板随配置保存、导出和回滚，不存储某次请求展开后的内容。

`headerVariables: true` 仅允许用于 `proxy`。控制台将代理动作切换为其他动作时清除该字段，其他动作继续使用现有固定 Header。沿用允许保存未完成草稿的工作流，导入或 API 保存草稿不额外增加完整语义校验；发布预检、发布和加载运行配置时拒绝不符合动作约束或模板规则的配置。

示例为路由的局部字段，不代表完整配置：

```json
{
  "headerVariables": true,
  "requestHeaders": {
    "X-Client-IP": "${remote_addr}",
    "X-Client-Port": "${remote_port}",
    "X-Original-Host": "${http_host}",
    "X-Trace-ID": "${request_id}",
    "X-Gateway-Route": "${site_id}/${route_id}"
  },
  "responseHeaders": {
    "X-Gateway-Trace": "${request_id}"
  }
}
```

## 3. 变量语法

- 使用 `${变量名}`，区分大小写，名称采用小写字母、数字和下划线。
- 一个值可包含多个变量和固定文本，例如 `client=${remote_addr}; route=${route_id}`。
- `$$` 表示字面量 `$`，例如 `$${remote_addr}` 输出原文 `${remote_addr}`；展开结果不递归解析。
- 普通美元符号原样保留。`$remote_addr` 不作为变量语法，界面和文档统一展示 `${remote_addr}`。
- 开启后，未知变量、空变量名、缺少结束括号等均为配置错误，不静默替换为空字符串。
- 关闭开关时不执行变量解析和美元符号转义，保持旧配置行为。

仅提供固定变量注册表和字符串片段拼接，不使用通用表达式引擎，不支持函数调用、脚本、环境变量读取或任意请求头读取。

## 4. 首版变量

下列变量均可用于代理请求头和响应头。它们以进入网关的原始请求及已匹配路由为依据，不以改写后的后端请求为依据。

| 变量 | 含义与取值来源 | 示例 |
| --- | --- | --- |
| `${remote_addr}` | 实际连接来源 IP，复用 `accessgate.SourceIP`，去端口，IPv4-mapped IPv6 规范化为 IPv4 | `192.0.2.10`、`2001:db8::10` |
| `${remote_port}` | 从 `r.RemoteAddr` 取得的客户端连接源端口 | `52310` |
| `${scheme}` | 客户端到 v2way 这一段的协议，由 `r.TLS` 判断 | `http`、`https` |
| `${host}` | 请求 Host 规范化后的主机名或 IP，去端口；使用现有域名处理规则 | `app.example.com` |
| `${http_host}` | 原始请求 `r.Host`，保留客户端提供的端口及 IPv6 方括号；不取同名普通 Header | `app.example.com:8443` |
| `${request_method}` | 原始请求方法 | `GET` |
| `${uri}` | 原始 URL 的转义路径 `r.URL.EscapedPath()`，不带查询参数，不受 StripPrefix 影响 | `/api/users` |
| `${request_id}` | 网关为本次请求生成的标识，与访问日志中的 ID 一致 | 本次请求 ID |
| `${site_id}` | 已匹配站点的配置 ID | `app-site` |
| `${route_id}` | 已匹配路由的配置 ID | `api-route` |

`${remote_addr}` 不信任 `Forwarded`、`X-Forwarded-For` 或 `X-Real-IP`。当前项目未实现受信代理链，因此经过前置代理或 NAT 时，该值仍是实际连接对端。`${scheme}` 同样不信任客户端转发协议头，也不代表后端目标的协议。

首版不提供完整查询串、Cookie、Authorization、任意 Header、上游响应状态、耗时或实际拨号地址变量。后几项需要不同的执行时机，不能混入本版的请求上下文变量。

## 5. 编译与运行时处理

### 配置校验和编译

新增独立的 Header 模板解析模块，由配置校验和网关编译共同使用，避免两套解析逻辑。解析结果为固定文本片段与变量标识，按快照保存为不可变的运行数据，每次请求不重新解析模板。

配置层仍保存原始字符串；编译结果不能写回草稿或配置版本。校验错误定位到站点、路由、请求/响应方向、Header 名称及错误变量，不在错误日志中输出完整 Header 值。开启变量的 Header 策略同时拒绝大小写不同但实际同名的重复键，避免 map 遍历顺序决定结果。

### 每个请求的处理顺序

1. 沿用现有站点、TLS SNI、访问控制、维护状态和路由匹配逻辑；未进入业务路由的响应不应用该路由模板。
2. 为已匹配代理路由创建请求级变量上下文，取原始来源、Host、协议、路径和日志请求 ID。StripPrefix、SetURL、PreserveHost 均不改变这些取值。
3. 展开并校验本次请求要使用的全部请求头和响应头，成功后再进入代理转发，不修改共享模板或配置 map。
4. 代理继续清理客户端伪造的转发头，并生成现有标准来源头；随后设置配置的普通请求头。
5. 按站点 `forwardAdminCookie` 开关执行管理 Cookie 策略，变量功能不能绕过该开关。
6. 应用响应 Header 策略，最后执行管理 Cookie 过滤及受保护站点 `private, no-store` 等强制规则。

运行时复查展开结果的长度和非法字符，单值仍最多 8192 字节，拒绝 CR、LF、NUL 及 HTTP Header 不允许的控制字符。来源值无法取得或展开后非法时，在发送后端请求或响应头之前返回 400，不发送部分展开的头部；错误信息不回显值。模板在发布时已经过校验，不应将未知变量留到请求阶段处理。

### 响应头的同名覆盖

对开启变量的代理路由，明确优先级为：**平台强制策略 > 路由配置 > 后端响应**。

路由显式配置的响应头使用替换语义，覆盖后端所有同名值；未配置的字段按现有代理行为透传。普通响应和 101 升级握手分别在其提交头部之前应用一次，避免提前设置在 ResponseWriter、随后又复制后端 Header 而形成重复值。代理失败时，已命中路由的响应头仍使用本次已验证的展开结果。

未开启变量的路由保留原有写入路径，本版不顺带改变旧路由响应头的同名追加行为。待后续统一 Header 策略时再单独处理这一兼容性变化。

## 6. 保留字段

沿用当前保留字段规则，不因支持变量而允许覆盖 `Host`、`Connection`、`Upgrade`、`Content-Length`、`Transfer-Encoding`、`Forwarded`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto` 等已保留字段；不扩大为对所有 `X-Forwarded-` 前缀的统一禁用。

网关已经自动设置来源头，无需配置 `X-Real-IP: ${remote_addr}`；需要传给业务自己的字段时使用 `X-Client-IP` 等普通 Header。Host 是否保留继续通过已有“保留客户端 Host”开关控制，WebSocket Upgrade 头仍由代理管理。

空字符串保持 Header 的既有设置语义，不作为删除指令；不新增追加、多值列表或删除 Header 的语法。

## 7. 控制台交互

继续使用路由编辑中的 JSON 文本框，首版不替换成新的表格编辑器。

- 高级区标题调整为“Header 策略”，代理路由增加“启用 Header 变量”开关，默认关闭。
- 开启后显示变量名称、用途和语法示例，可复制变量；不要求访问外部文档才能知道来源 IP 变量怎么填写。
- 变量开关影响请求头与响应头两个文本框；关闭后保留原文并按固定字符串保存，不自动替换文本。
- 前端检查 JSON 对象结构、字符串值和模板语法，服务端执行权威校验。失败保留编辑内容，错误定位到具体 Header。
- “保留编辑”“保存草稿”“发布”的现有流程保持一致；发布预览列出开关与原始 Header 模板的变化，不展示某次请求值。

变量帮助内容与后端注册表保持一致，通过测试核对名称集合。首版不为此新增管理 API；页面不存储真实请求的展开快照。

## 9. 验收

1. 缺少开关的旧配置对 `${remote_addr}` 和 `$$` 均保持原文；开启后正确处理单变量、混合文本、多个变量与转义，关闭再开启不会改写原始字符串。
2. IPv4、IPv6、IPv4-mapped IPv6、带端口 Host 取值正确；伪造来源头和协议头不能影响 `${remote_addr}` / `${scheme}`。
3. StripPrefix、后端 URL 和 PreserveHost 不改变原始请求变量；请求头和响应头的 `${request_id}` 与日志 ID 相同。
4. 拒绝未知/畸形变量、非法动作、保留字段、大小写重复 Header 和超长展开；错误不回显敏感值，也不访问后端。
5. 普通 HTTP、SSE 和 WS/WSS 握手均正确设置 Header；流式正文不缓冲，升级后不再次求值；发布期间存量连接使用原快照。
6. 同名响应头按开启模式的替换规则生效，旧关闭模式保持原行为；管理 Cookie 策略与 IP 授权缓存策略始终生效。
7. 并发请求间变量不串值，模板和运行快照无可变共享状态；`go test -race ./...` 通过。
8. 控制台开关、复制变量、错误保留、草稿往返和发布预览通过前端类型、交互与格式检查；长 JSON、手机和短横屏下仍可编辑及提交。
