# 安全审查记录（2026-11-05）

## 范围与结论

对管理认证与会话、CSRF/Host 校验、业务代理、静态文件访问、IP 授权、证书存储、前端危险 HTML 操作及部署入口进行了代码检查。确认一项有部署前提的高危会话泄露问题、一项中危可用性问题，并发现默认 Compose 的管理入口暴露风险。以下问题描述保留最初审查结果；经用户授权已实施修复，当前行为及验证见文末“修复记录”。

验证仅使用临时账号、临时目录和回环模拟服务，没有访问实际凭据、启动开发环境或进行实际拒绝服务攻击。没有检查线上部署、容器运行状态、实际防火墙及第三方依赖最新漏洞公告，不能将本次结果视为完整渗透测试或依赖安全证明。

## S1：管理会话可能经同主机名业务代理泄露（高危，有条件）

- 代码位置：`internal/admin/auth.go:148`、`internal/gateway/gateway.go:504`、`internal/admin/auth.go:101`。
- 管理 Cookie 使用 `v2way_session`，路径为 `/api/admin/v1`。Cookie 不按端口隔离，`HttpOnly`、`SameSite=Strict` 和 `Secure` 均不能阻止同主机名、同协议的跨端口发送。
- 业务代理保留客户端 Cookie，没有剔除管理会话。管理入口和业务入口使用同一个主机名或 IP、不同端口时，访问业务端口的 `/api/admin/v1/...` 路径可把管理会话交给匹配的业务后端。宽泛的 `/` 前缀代理即可满足路径条件。
- 攻击需要管理员浏览器已有有效会话，并访问相应业务路径；攻击者需要控制该业务后端或能够读取其请求 Cookie，且能够连接管理 API。无需先知道管理密码。不同主机名且使用当前 host-only Cookie 时，不满足此跨端口泄露条件。
- 截获的会话可直接重放。管理会话 GET 接口返回 CSRF 令牌，攻击者可使用独立 HTTP 客户端设置 Origin 和 CSRF 请求头继续写入。现有 CSRF 防护不能保护已经泄露的会话。
- 隔离测试已复现完整链路：临时管理员登录 → Cookie jar 向同主机名业务端口发送 Cookie → 实际代理后端截获 Cookie → 重放管理会话读取 CSRF → 成功 PUT 草稿。另验证 Secure Cookie 也会发往同主机名的其他 HTTPS 端口。
- 建议：业务代理转发前剔除平台管理 Cookie，保留应用自己的 Cookie；考虑同步隔离业务响应对平台保留 Cookie 的写入。部署时给管理入口使用独立主机名，避免与不可信业务共用主机名。仅增加 Secure 或修改端口不能解决问题。补充跨端口、HTTPS 与普通应用 Cookie 保留的回归测试。

## S2：匿名慢速请求正文缺少读取期限（中危，可用性）

- 代码位置：`cmd/v2way/main.go:231`、`internal/admin/server.go:50`、`internal/admin/auth.go:108`；业务监听的类似超时配置见 `internal/gateway/listeners.go:90`。
- 管理服务器只设置 ReadHeaderTimeout 和 IdleTimeout，没有请求正文读取期限。登录接口在认证前使用 `io.ReadAll` 读取最多约 16 MiB 正文；字节上限不能限制等待时间，请求头读取期限和 keep-alive 空闲期限也不能限制正文读取。
- 能连接管理入口的未登录客户端可发完合法请求头后停止或缓慢发送正文，持续占用连接和处理 goroutine。每 IP 每分钟五次的登录限制只限制新尝试，已进入正文读取的连接不会因此到期；长期或多来源请求可积累资源占用。
- 隔离测试确认：与生产相同的 HTTP 服务器超时设置下，匿名请求等待 11 秒才发送正文，仍可继续进入认证，超过配置的 10 秒请求头期限。另一测试确认单纯取消请求上下文不会解除正在等待的正文读取。没有实施大量连接压测，未测量实际耗尽阈值。
- 建议：为登录等短请求设置明确的连接读取期限和更小的正文上限，限制并发处理/连接数量。业务请求按上传、下载、SSE、WebSocket 场景设置读取及写入策略，避免统一短 WriteTimeout 破坏流式连接。

## D1：默认 Compose 直接发布明文管理端口（部署风险）

- 代码位置：`docker-compose.yml:15`、`deploy/entrypoint.sh:5`。
- Compose 使用 `4033:4033`，容器默认监听 `0.0.0.0:4033`，管理服务只提供 HTTP。是否能从公网连接取决于宿主网络、防火墙和安全组，本次没有验证实际暴露。
- 若可远程直连该端口，直接通过 HTTP 登录会明文传输管理密码和会话，并扩大 S2 的可达范围。另有 HTTPS 代理并不会自动关闭这条 HTTP 访问路径。
- 建议：宿主端口绑定回环地址或仅允许可信管理网段访问，经独立 HTTPS 管理域名使用控制台；按实际容器代理拓扑配置网络访问限制。此处是部署约束建议，不代表当前线上已经泄露。

## 修复记录

- 站点新增 `forwardAdminCookie`，缺失或 false 时默认剔除业务代理请求中的 `v2way_session` 和后端响应中的同名 Set-Cookie，保留普通应用 Cookie；包含多行和重复管理 Cookie 的过滤。用户明确要求仅按开关执行，开启后双向保留，不限制后端地址。
- 站点配置的“访问策略与请求限额”提供“转发管理会话 Cookie”，草稿保存并发布后生效；发布预览展示“转发/剔除”。已有配置缺少该字段时默认剔除；用于代理管理控制台的站点需要显式开启再发布。
- 管理服务器设置请求头 10 秒、请求头与正文总读取 15 秒；登录正文上限收紧到 8 KiB，最多 16 个并发登录，超额返回 429。业务监听的上传、SSE、WebSocket 策略保持独立。
- 首次安全修复将管理端口限制为宿主回环；后续部署配置采用 host 网络，入口脚本默认直接监听 `127.0.0.1:4033`，不设置端口映射。远程初始化需 SSH 隧道或可信网络配置；本地配置变化没有自动修改实际部署或重建容器。
- 新增正式回归测试覆盖默认过滤、普通后端开关往返、重复 Cookie、开启后的管理代理登录/读取会话/退出、过大登录正文、并发登录限额及真实 HTTP 慢正文到期。
- 验证：`go test -race ./...` 通过；前端 59 项测试、`npm run typecheck`、`npm run format:check` 通过；`docker compose --env-file /dev/null config --quiet` 通过。
- 没有启动开发环境、构建镜像、更新真实站点配置、初始化或重置真实账号，也没有执行 Git 操作。
