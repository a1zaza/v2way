# v2way 统一网关设计方案：JSON 文件持久化版

> 编写时间：2026-10-30 16:50:16 +08:00
>
> 状态：JSON 持久化主体已实施（2026-11-01），使用方式与边界见 [JSON 存储说明](json-storage.md)。
>
> 本文替代原方案中的 SQLite 选型与相关事务设计。网关能力、独立项目定位及前端风格沿用 [原设计方案](unified-gateway-design.md)；当前代码已去除 SQLite 运行依赖；本文的完整故障验收矩阵仍包含后续验证项目。

## 1. 调整结论

v2way 不使用 SQLite 或其他数据库。网站的域名、路由、后端服务、访问策略和证书引用统一保存在 JSON 文件中，由 Go 服务读取、校验并生成内存运行快照。

继续保留“编辑 → 保存草稿 → 校验 → 发布 → 回滚”的管理流程。浏览器编辑不会直接修改运行配置，业务请求只访问内存，不逐请求读取磁盘。

技术栈调整为：**Go 网关与管理服务 + React / TypeScript 中文控制台 + JSON 文件存储**。仅移除持久化数据库依赖，不改变独立部署定位；Termical、vxv 仍仅作为前端视觉与交互参考。

## 2. 存储边界与简化原则

| 数据 | 保存方式 | 说明 |
| --- | --- | --- |
| 当前已发布网站配置 | `gateway.json` | 完整配置与发布元信息，唯一的持久化生效依据 |
| 尚未发布的草稿 | `draft.json` | 配置、修订号和编辑所依据的运行版本 |
| 历史配置 | `versions/<版本号>.json` | 不可变快照，用于查看与回滚 |
| 管理员 | `account.json` | 用户名、密码摘要、账户修订号；不保存明文密码 |
| 登录会话 | 进程内存 | 保存令牌摘要、CSRF 和有效期，重启后重新登录 |
| 证书 | `certificates/<证书标识>.json` | 元数据及加密后的证书材料，一张证书一个文件 |
| 证书主密钥 | `master.key` | 保持现有独立密钥设计，不混入网站配置 |
| 审计记录 | `logs/audit-YYYY-MM.jsonl` | 逐行 JSON，按月轮转，不反复重写整个数组 |
| 访问日志 | 当前内存队列 | 先保留现有行为；后续可独立增加 JSONL 轮转 |
| 运行指标、后端健康 | 进程内存 | 重启重新统计，不写回网站配置 |

不增加通用数据库抽象、分布式锁或跨节点同步。首版仍是 Linux 本地文件系统、单实例写入。网络共享文件系统、跨文件系统替换和多实例共写不在支持范围内。

网站配置集中在一个文件中，避免每个站点各自落盘导致一次发布只更新了一部分站点。历史、账户与证书文件各自独立，不把它们假设为一个跨文件事务。

## 3. 数据目录

```text
.data/
  gateway.json                   已发布配置与发布索引
  draft.json                     草稿与修订信息
  account.json                   管理员密码摘要
  master.key                     证书加密主密钥
  instance.lock                  单实例排他锁
  versions/
    000000000001.json            不可变历史快照
    000000000002.json
  certificates/
    <证书标识>.json              元数据与加密材料
  logs/
    audit-2026-10.jsonl          审计日志
```

- 数据目录及子目录权限 `0700`，配置、账户、证书和密钥文件权限 `0600`。
- 临时写入文件与目标文件位于同一目录，名称由程序生成，例如 `.gateway-<随机值>.tmp`。
- 文件名只使用程序生成的标识，不使用域名、站点名称或用户提供的任意路径拼接。
- 保留现有 `instance.lock` 的 `flock` 机制；进程退出释放锁，文件留存不代表实例仍在运行。
- 数据目录及其子目录仍不能成为业务静态目录。

## 4. 网站配置格式

### 4.1 当前运行文件

`gateway.json` 是包含发布信息的完整配置文件，结构示意如下。以下仅展示外层结构，`config.sites`、`config.upstreams` 沿用现有完整对象模型：

```json
{
  "schemaVersion": 1,
  "version": 12,
  "createdAt": "2026-10-30T16:50:16+08:00",
  "release": {
    "requestId": "由客户端生成的唯一请求标识",
    "payloadHash": "发布请求内容的 SHA-256 摘要",
    "actor": "admin",
    "sourceRevision": 8,
    "expectedActiveVersion": 11,
    "note": "调整接口代理规则",
    "rollbackFrom": null
  },
  "configHash": "规范化 config 的 SHA-256 摘要",
  "history": [
    {"version": 11, "snapshotHash": "上一版本快照摘要"}
  ],
  "config": {
    "sites": [],
    "upstreams": []
  }
}
```

业务对象保持以下关系：

| 对象 | 继续保存的内容 |
| --- | --- |
| 站点 | 标识、名称、域名、启用状态、HTTPS、证书引用、请求限制与 IP 策略 |
| 路由 | 标识、路径/方法、匹配方式、代理/静态/响应/跳转动作、头部策略与超时 |
| 后端池 | 标识、名称、目标地址、权重和健康检查路径 |

配置文件不保存管理员密码摘要、会话、证书私钥、实时健康状态和访问日志。证书通过 `certificateId` 引用独立的受保护文件。

`schemaVersion` 表示文件格式版本，`version` 表示发布版本，二者独立。版本号限定为 JavaScript 可安全表示的正整数；未首次发布时以虚拟版本 `0` 和空配置运行，不预先生成虚假的发布记录。

`configHash` 用于识别配置变化和检测意外损坏，不是防止本机恶意修改的签名。能够修改数据目录的用户本身处于实例的信任边界内。

### 4.2 草稿文件

`draft.json` 包含 `schemaVersion`、`revision`、`baseVersion`、`updatedAt`、`updatedBy` 和 `config`。

- 每次成功保存使 `revision` 加一；API 必须携带编辑时读取的修订号。
- `baseVersion` 表示草稿建立或重置时依据的运行版本，不因发布过程另写一次草稿文件。
- 已保存草稿与当前运行配置是否一致，通过规范化配置内容或摘要判断，不单凭修订号推断。
- 发布和回滚只提交运行文件，不强制重写草稿；因此发布成功后，不存在“草稿更新失败导致发布结果未知”的跨文件依赖。
- 草稿允许暂时不完整，但必须满足 JSON 结构、字段类型、大小和数量限制。发布时再做完整语义与资源校验。

### 4.3 历史文件及索引

每个历史文件保存与该次 `gateway.json` 相同的完整快照，发布后不修改。

`gateway.json.history` 按从新到旧列出保留的已提交历史，默认保留前 100 个版本。当前版本额外保留，不计入这 100 个历史版本。版本列表展示当前版本及该索引引用的历史，不能将 `versions/` 下每个文件都当成已成功发布。

候选历史文件可能已经落盘，但发布尚未提交；这种文件属于孤立候选，不进入历史列表，也不能被回滚接口直接选择。下一版本号需跳过已有候选文件名，不能覆盖或复用其编号。

索引与快照摘要用于验证引用。清理时只删除当前文件和保留索引都未引用的旧文件；不在发布提交前删除历史。回滚历史配置时创建新版本，不直接覆盖历史文件。

## 5. JSON 解析与写入约定

### 5.1 可读且确定的格式

- 使用 UTF-8、两空格缩进和结尾换行，便于查看和比较。
- 对象字段采用稳定序列化规则；保留具有业务语义的数组顺序，不为计算摘要随意重排规则。
- 摘要基于规定的规范化编码计算，不直接依赖用户文件的空白、缩进或键顺序。
- 拒绝重复键、未知字段、尾随内容、非整数版本号、不支持的 `schemaVersion`、超大文件和过深嵌套；Go 的 `DisallowUnknownFields` 本身不负责拒绝重复键，需额外检查。
- 发布文件建议初始上限 8 MiB，配置对象仍沿用站点/后端各 500 个、路由总数 5000 条的数量上限；草稿与管理请求按明确的相应上限校验，避免请求与文件大小限制互相矛盾。

### 5.2 原子文件替换

统一提供内部 `atomicWriteJSON` 工具，执行：

1. 在目标文件同目录创建唯一临时文件，权限 `0600`。
2. 完整写入 JSON，检查写入字节数和错误。
3. 同步文件数据，检查 `Sync` 和 `Close` 的结果。
4. 以 `rename` 替换目标路径。
5. 同步目标文件的父目录，确认目录项持久化。

不直接截断或原地覆盖正在使用的文件。现有文件在替换前保持完整，替换后读取者获得完整的新文件。Linux 的替换语义和落盘保证需要分别处理：原子替换不能代替文件与目录同步。[Linux rename 手册](https://man7.org/linux/man-pages/man2/rename.2.html)、[Linux fsync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)

这套保证限定在受支持的 Linux 本地文件系统上，不泛化为所有平台；Go 的 `os.Rename` 文档也提示非 Unix 平台的原子性边界。[Go 文件操作文档](https://pkg.go.dev/os#Rename)

若替换已经发生，但父目录同步失败，不能简单返回“写入失败，旧文件未变”。应报告结果待确认，读取可见文件并重新确认其同步状态，暂时禁止后续写操作；磁盘状态无法确定时保持已有运行快照并要求恢复处理。

## 6. 编辑、发布与运行一致性

### 6.1 保存草稿

进程内使用写互斥锁串行处理管理变更。保存前核对 `revision`，并核对上次读取的文件摘要，发现外部修改或并发编辑时返回 `409`；不覆盖新内容。

只有 `draft.json` 成功持久化后才更新内存草稿缓存并返回新修订号。发生结果待确认时，浏览器保留本地编辑，重新读取服务器状态；不得无条件重发旧草稿。

进程锁只约束遵守锁协议的进程，不能阻止普通编辑器修改文件。文件摘要检查可发现已经发生的修改，不能为不遵守协议的外部写入提供原子比较并交换保证；因此运行期间不支持直接编辑权威文件。

### 6.2 发布步骤

发布请求包含 `requestId`、`revision`、`expectedActiveVersion`、备注和可选回滚版本。

1. **去重与并发检查**：同一请求标识、同一请求摘要返回原结果；相同标识对应不同请求返回 `409`。新请求核对草稿修订和当前运行版本。
2. **校验与准备**：完整校验域名、路由、引用、静态目录、证书和资源约束，编译候选内存快照；此阶段不切换数据面。
3. **分配版本**：在写锁内选取未使用版本号，生成不可变候选快照和新的保留历史索引。
4. **持久化历史**：先写入候选 `versions/<版本号>.json`，同步文件及目录；失败则结束，当前运行配置不变。
5. **提交运行文件**：原子替换并同步 `gateway.json`。这是唯一的持久化提交点，无需另写活动版本指针或索引文件。
6. **激活快照**：磁盘提交成功后原子切换内存指针，更新内存发布索引；该步骤只切换已准备好的对象，不再执行可能失败的磁盘操作。
7. **返回结果**：返回版本号、请求标识和运行版本；补充审计日志，按保留策略清理无引用旧文件。

磁盘提交和内存指针切换仍不是一个跨介质原子事务。提交完成至切换之间的极短窗口内，请求可能继续使用旧快照；若此时进程退出，下次启动从已提交的新文件恢复。已经持久化的新版本不会被报告为“发布失败并恢复旧版”。

新请求使用激活后的快照；已建立 WebSocket/SSE 延续旧快照。回滚也是一次新发布，需要重新校验证书和目录，不回滚管理员或密钥文件。

### 6.3 结果查询与幂等边界

- `requestId` 和请求摘要随成功快照保存，当前与保留历史构成可重建的发布回执索引，不单独维护数据库或另一个必须同步提交的回执文件。
- 客户端超时后先按原请求标识查询，再判断是否重试；重试仍使用相同请求标识与原始参数。
- 幂等结果保证覆盖当前及保留历史。历史回执已清理时明确返回“未知或已超出保留范围”；旧请求的 `expectedActiveVersion` 检查防止其被误当成新的发布重复执行。
- 候选文件存在不代表发布完成。结果待确认、已提交并激活、未提交和回执超出范围需明确区分。

## 7. 启动与异常恢复

| 场景 | 处理方式 |
| --- | --- |
| 从未发布，当前及历史文件均不存在 | 使用虚拟版本 0 的空配置；管理账户仍须显式初始化 |
| 当前文件合法且资源可用 | 校验并加载当前版本，重建历史与幂等查询索引 |
| 当前文件存在但 JSON 损坏或格式不支持 | 拒绝业务启动并显示恢复原因，不静默重建空配置 |
| 当前文件缺失，但已有历史/其他已发布迹象 | 视为异常，要求显式恢复，不能当成首次安装 |
| 临时文件或未提交候选遗留 | 不激活；按引用关系识别并延后清理 |
| 历史索引引用文件缺失或摘要错误 | 当前版本可独立验证时继续业务服务；标记历史损坏，冻结发布、回滚及清理，直至修复 |
| 草稿损坏但当前版本正常 | 保留业务服务，禁用草稿写入；允许显式从当前版本重建草稿，保留损坏原件 |
| 证书私钥/主密钥缺失或无法解密 | 明确报告，不能换新密钥掩盖已有材料丢失 |

恢复命令应在离线状态下选择可验证的历史版本，经校验后显式重建当前文件；不因为“目录里版本号最大”就认定它曾提交成功。损坏文件应保留为受保护的故障副本。

## 8. 账户、证书、会话与审计

### 8.1 管理员及会话

`account.json` 保存格式版本、用户名、Argon2id 参数/盐/摘要、账户修订号和变更时间。初始化使用独占锁与原子文件操作，不覆盖已有账户，也不提供默认密码。

会话使用有界内存表，仍只保存令牌摘要，包含 CSRF、账户修订号与绝对过期时间；定时清理过期会话并设置总量上限。重启后全部会话失效，这是从当前 SQLite 会话持久化调整后的明确行为。

修改密码先持久化新的账户修订，再更新内存账户并撤销旧会话。账户修订不匹配的会话拒绝访问；重启后没有旧会话可以复用。

### 8.2 证书文件

一张证书的元数据、算法版本、随机 nonce 和密文保存在同一个 JSON 文件中。密文字段用 Base64 编码；继续使用 AES-256-GCM，证书标识与格式版本绑定为认证附加数据。

上传时先解析证书、校验私钥、SAN 与有效期，再将整个文件持久化；全部完成后才返回可引用的证书标识。管理 API 只返回从实际材料校验过的元数据，不回传私钥和密文。

证书更新生成新标识，发布站点配置切换引用。删除前检查当前、草稿和保留历史引用；首版可先保留无引用证书，不自动删除可能影响回滚的材料。

### 8.3 审计日志

JSONL 日志按单一写入器追加，每条包含事件标识、时间、操作者、动作、结果及对象标识；设置单条上限和文件轮转。启动时只允许处理最后一条因中断形成的不完整记录，中间损坏不能静默跳过。

发布快照内的发布元信息是权威记录，JSONL 是方便检索的审计视图，可按事件标识补记去重。发布提交后的日志追加失败应报告日志降级，不将已经提交的发布伪装成失败，也不重复执行业务变更。

账户、证书等独立文件操作需明确记录尝试和结果；不承诺 JSONL 与所有文件之间具有数据库事务级的全局原子性。网站发布的追溯证据始终随快照一起持久化。

## 9. 配置导入、人工编辑与备份

- 控制台导出继续提供纯 `sites` / `upstreams` 配置，便于人工维护；完整 `gateway.json` 属于带发布记录的运行文件，二者需明确区分。
- 增加“导入 JSON 为草稿”入口，支持纯业务配置及受支持的完整文件。导入完整文件时只提取业务配置，不接受外部提供的发布版本、历史索引或账户身份作为本机权威状态。
- 人工编辑建议在导出的 JSON 副本上进行，通过导入、校验和发布生效；首版不通过文件监听自动应用磁盘变动。
- 离线工具如 `config import -file` 与恢复命令也必须获取同一实例锁；运行中无法获取锁时明确提示通过管理 API 操作。
- `check -file` 扩展为识别纯业务配置和完整配置的格式，区分结构校验与运行资源校验，不触发写入或发布。
- 完整备份需要在同一管理写锁下读取受支持的文件集合，或正常停机后备份整个数据目录。运行中随意复制多个文件并不保证一致快照。
- 普通配置备份不含秘密；完整备份若包含 `master.key` 与证书密文必须按秘密材料保护，不能宣称密文与解密密钥打包后天然安全。

## 10. 现有实现改造范围

| 位置 | 拟调整内容 |
| --- | --- |
| `internal/store` | 移除 `sql.DB` 与 SQL；实现 JSON 文件模型、原子写入、修订检查、历史索引和恢复 |
| `internal/admin/auth.go` | 通过账户存储接口读写管理员；会话改为有界内存表 |
| `internal/admin/server.go` | 发布顺序改为先持久化再激活；新增运行版本前置条件、导入及明确的待确认结果 |
| `internal/certificate` | 去除数据库调用，使用独立加密 JSON 证书文件 |
| `cmd/v2way` | 首次初始化、启动格式检查、离线配置导入/恢复入口 |
| `web/src` | 发布参数、结果待确认提示、JSON 导入与重启会话失效反馈 |
| `go.mod` / `go.sum` | 移除 SQLite 驱动及仅由其引入的传递依赖，保留实际仍使用的密码/网络/文件锁依赖 |
| 测试与运维文档 | 数据库事务故障替换为文件系统故障注入，更新数据目录与备份说明 |

网关协议处理、中文页面风格和网站对象字段尽量复用。存储模块提供账户、配置、证书和审计的具体方法，不把文件路径、密钥或内部状态机暴露给前端。

如发现现有 `gateway.db`，新版不得静默忽略并初始化为新实例。若确有需保留的数据，另行提供离线的一次性格式转换：校验并保留原库与原密钥，导出至新的 JSON 数据目录，经验证后人工切换。正常运行包不因此继续携带 SQLite；没有旧数据时直接使用 JSON 初始化，不安排无意义的数据转换任务。

## 11. 验收重点

1. **无数据库依赖**：正常编译、初始化、建站、登录、证书、审计、发布和回滚均不依赖 SQLite；不生成 `gateway.db`。
2. **配置闭环**：网站配置确实来自 JSON，草稿保存不影响当前流量；重启恢复到已提交版本，重启会话失效。
3. **写入故障**：短写、权限不足、满盘、文件同步失败、替换失败和目录同步失败分别注入，验证旧/新文件完整及结果状态。
4. **中断恢复**：在历史落盘、当前文件替换、目录同步、内存切换和响应返回等边界中断，验证不激活孤立候选、不覆盖未知结果。
5. **并发与重试**：多标签页草稿冲突、重复发布、同标识不同内容、历史回执清理后的旧请求、外部文件修改以及多进程锁冲突。
6. **解析与完整性**：重复键、未知字段、尾随 JSON、超大/深层输入、未知格式版本、损坏草稿、损坏历史和摘要不匹配。
7. **秘密与目录隔离**：私钥不进入业务配置、错误或导出；权限正确；历史引用证书不被删除；文件名、路径及符号链接不能逃逸数据目录。
8. **原有协议回归**：保留代理、WebSocket 热发布、SSE 刷新/取消、TLS 域名隔离、静态目录和 Range 等现有测试。
